# 金蝶下推链 —— 复用指南

> 结论先行：**可复用了**。以前每来一家客户就得现写脚本（扣款金额、目标值硬编码在文件里），
> 现在统一入口 `src/push_chain.py`，一条命令跑完
> 「出库单 → 应收单（含折扣分摊）→ 专票 → 凭证」，换客户只换参数。

---

## 一、以后怎么用（三种典型场景）

### 1) 先验算，不动账（推荐每次都先跑这个）
```bash
python src/push_chain.py --customer 广源包装集团 \
    --bill-nos XSCKD-105-202608-0121,XSCKD-105-202609-0020 \
    --discount 2733.5 --target-notax 266824.88 --target-tax 34687.22 \
    --dry-run
```
只做筛选 + 读明细 + 打印分摊与对齐方案，**不下推、不保存**。

### 2) 正式全链（含扣款）
```bash
python src/push_chain.py --customer 广源包装集团 \
    --date-from 2026-08-21 --date-to 2026-09-20 \
    --discount 2733.5 --target-notax 266824.88 --target-tax 34687.22 \
    --biz-date 2026-09-30 --invoice-date 2026-09-30 \
    --yes
```
- `--date-from/--date-to` 按**单据日期 FDate** 筛（用户 2026-10-29 确认口径；也可用 `--bill-nos` 直接点名单号）
- `--discount` 给了就按行含税占比分摊到折扣额；`--target-notax/--target-tax` 给了就闭环对齐
- `--yes` 放行不可逆动作（保存/提交/审核/生成凭证）；**不加就只做到保存为止**
- `--no-invoice-merge` 下推专票用「**分录不合并**」→ 专票逐行对应应收单 → **不产生
  `-00000N` 子单**（代价：专票行数 = 应收单行数）。原因与另两条路见
  [`广源应收单子单-原因分析.md`](广源应收单子单-原因分析.md) 第八节

### 3) 分步跑，中间人工核对
```bash
--step receivable   # 只到应收单保存
--step invoice      # 到专票保存
--step voucher      # 全链（默认）
--ar-no AR105-...   # 复用已有应收单，跳过筛选/建单（只跑 invoice/voucher）
```

### 4) 验收：有没有多出子单
```bash
python src/check_subbills.py AR105-202609-0004 --detail   # 只读；期望「子单数 = 0」
```

### 想批量走 Excel？用原来的 `src/run.py`
`run.py`（Excel 驱动、多客户分组、结果回写）和 `push_chain.py`（命令行、临时一单）
**共用同一套引擎**（`KingdeeUI` + `discount.py`），不需要维护两份逻辑。

## 二、能自动化到什么程度

| 环节 | 自动化 |
|---|---|
| 清重复标签 → 筛单 → 硬校验单据齐不齐 → 勾选 | ✅ 全自动 |
| 下推应收单 → 填业务日期 | ✅ |
| **折扣额按行含税占比分摊 + 尾差补最大行** | ✅ 全自动 |
| **总不含税/总税额闭环对齐到实际开票** | ✅ 全自动 |
| 保存应收单 → 下推专票（分录合并）→ 回填日期/复核人 | ✅ |
| 生成凭证 → 查报告 → 清场只留出库单列表 | ✅ |
| **凭证「审核」** | ⚠️ 默认不做，等你发话 |

## 三、仍需人来定的四件事（无法从系统里自动取得）

1. **扣款金额**和**实际开票的不含税/税额** —— 来自电子税务局的票，脚本读不到，得你给。
2. **立账类型**（业务应收 / 暂估应收）—— 口径未定，尚未采集。
3. **凭证摘要取数**（月份按发票月还是货款月）—— `digest_enabled` 仍是 false。
4. **凭证审核**是否现在点 —— 按钮已可用，一直留着等你确认。

## 四、本次顺带修掉的 3 个静默 bug（都会"不报错地做错事"）

| # | 问题 | 现象 | 修法 |
|---|---|---|---|
| 1 | 过滤条件**末行被静默丢弃**（金蝶异步 commit） | 4 张单只筛出 **3 张**（46 行→36 行），日志却显示"设置成功" | 写值后等 450ms、确定前等 1200ms + `_read_condition_rows()` 回读自检 |
| 2 | 行级复选框**合成事件勾不上** | 点了 46 个复选框，「真实选中 0」；且老实现命中的是**隐藏页面**的列表 | 限定可见 grid + `page.mouse.click(x,y)` 逐行真实点击 |
| 3 | 表头复选框是**三态**语义 | 「只勾 1 行」点一下变 **565 行全选**，后续勾选全乱 | `clear_selection()` 循环点表头直到 `selected_count()` 归零 |

第 3 条也解释了此前记录里的「首屏残留 555 行选中」之谜。

**外加两道工程防线**（`push_chain.py` 内置）：
- 开始前清掉**重复的同名标签**（两个「销售出库单列表」并存 → 过滤条件落到另一个实例 → 静默漏单）
- 筛选后**硬校验单据号集合**，缺单/多单直接停
